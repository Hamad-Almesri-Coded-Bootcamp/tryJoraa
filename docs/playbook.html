What Jur'ah is, in three lines

A patient keeps every prescription they hold, from any clinic or hospital, in one profile. They see today's doses and mark them taken or skipped. When a dose is missed, an agent checks whether it can safely be caught up. It proposes a new time the patient accepts, or it refuses and tells the doctor. Every change is written to an audit trail.

Who does what

Each person owns one lane and one branch. The lead's machine also runs the boss session, which is the only thing that touches main. You never touch another lane's files. If you need one, you write it down as a dependency and keep going.

Boss main

Runs on the lead's laptop on a timer. Never writes a feature. Merges cleared pull requests, runs the three gates, reverts if a gate goes red, keeps the lane branches current, ticks the checklist.

  • Commands: /ship every 45 min, /close at 23:00
  • Owns: CLAUDE.md, checklist, technical plan, CI, skills

How work moves from your laptop to the live site

You never merge, pull, rebase or open a pull request by hand. /work does your side. /ship does the boss's side. This is the whole path.

01 · you/work picks a taskfrom your plan file, builds it inside your lane
02 · youProves itruns the test, npm run build, shows you the real output
03 · youReviewer subagentchecks the diff against the checklist until it says SAFE TO MERGE
04 · youCommit, push, PRunder your own name, on your own branch
05 · bossCI + integrator judge itMERGE, MERGE AFTER, or DO NOT MERGE with the exact fix
06 · bossMerge to mainsquash, then Vercel deploys
07 · bossThree gates on the live sitebuild · verify:rls · verify:ui. Red → the merge is reverted at once
08 · bossmain flows back to youmerged into a/data, b/ui, c/agent. Checklist ticked from main only
Why this is safe

The boss can merge without a human because it can also revert without a human. main is never left broken between two runs. Your branch always has the latest main before you start the next task.

Your day, from start to finish

The same shape every day. It is short on purpose.

  1. Open a terminal in the repo. Check you are on your branch: git branch --show-current. That is the one git command you may type.
  2. Type /work. It fetches everyone's latest work, reads your plan, and says in three lines what is done, what is next, and what is blocked. Then it starts the next task without asking.
  3. Watch for proof, not claims. Every task ends with real output on screen: a test log, a screenshot, a query. If you see "done" without output, say "show me the output".
  4. Answer when it stops. It stops for four things only: a credential, a decision about what we build, a task blocked on another lane, or anything that would make the app less safe. The answer to the last one is always no.
  5. Ten-minute team check, twice a day. Each person reads their three lines aloud: done, next, blocked. Owner C draws the agent flow once a day from memory. Everyone explains their lane once.
  6. End of day: nothing to do. The boss runs /close at 23:00, scores the checklist, writes the failures log, and posts each lane's first task for tomorrow.
Every day, without fail

Your own name must appear in the commit list every day. Claude commits as whoever the laptop says it is, so set git config --global user.name once and never commit from someone else's machine.

Rules that never bend

Claude is instructed to follow all of these itself. If it ever offers to break one, the session has gone bad: /clear and start again.

Stop and ask, every time

  • A credential you do not have. Never invent one.
  • Dropping a feature to make Thursday. Team's call.
  • Weakening a security policy to make something pass. The feature is wrong, not the policy.
  • Deleting or rewriting work already pushed.
  • After Wednesday 22:00. Nothing merges.

Security

  • The service role key never reaches the browser, a commit, or a chat. Only seed-auth.ts touches it.
  • Every table has row-level security on. Every write policy has with check.
  • Every change to patient data lands in audit_log by trigger. Nobody writes it directly.
  • Every typed field is validated on the server with Zod.

The agent

  • It decides which tool to call. It never decides what time. All arithmetic runs in SQL or a Code node.
  • No agent ever writes a prescription. Drafts and proposals wait for a human.
  • Unknown means refuse. Never "probably fine".
  • The browser never calls n8n. It calls /api/runs.

Never type these

  • git push --force
  • git reset --hard
  • git checkout ., git clean
  • git rebase. Nobody rebases. The boss merges main into your lane.
The one sentence to remember

Never say a thing is done. Show the output that proves it. Not a summary of the output. The output.

Changing the plan is normal. Working around it is not.

The plan will be wrong somewhere. That is expected. What is fixed is how it changes, so nothing gets lost and nobody is surprised.

Your own task list

Yours to change. Reorder, split, reword tasks in .plans/<you>.md and say so in the next PR. Adding a task is fine if it serves a judged item or a numbered decision. Dropping one is a team decision.

A product decision

The lead adds the next D number to PRODUCT-DECISIONS.md and puts a one-line "superseded by" note on the old one. Numbers are never reused. Then the affected files are fixed in place.

The workflow itself

A skill, a reviewer rule, CI, CLAUDE.md in your way? Write the exact change under ## Workflow proposals in your plan file, with the task it blocked. The boss applies or declines it on the next /ship.

Something is stale

Fix the text in place. Never add an "amendments" section under the wrong text. Two documents that disagree is a bug to fix, not history to keep.
